## 資料庫現況

**M1.2 新增的 migrations**（依序）：

```
m1_2_bookings_schema_rls
m1_2_create_booking_rpc_and_free_on_cancel
m1_2_harden_function_execute_grants
m1_2_dedupe_bookable_slots_and_unique_start
```

**新表 / view**：

```
bookings(id, customer_id -> profiles, service_id -> services,
         status check(pending_payment|paid|cancelled) default 'pending_payment',
         price int NOT NULL, paid_at, payout_id, created_at, updated_at)
         -- 沒有 start_slot_id / slot_id / barber_id / 拆帳欄位
booking_slots(booking_id -> bookings on delete cascade,
              slot_id -> bookable_slots on delete restrict,
              primary key(booking_id, slot_id))
              -- uniq_slot_held: unique index on (slot_id) ← 防雙訂的全部機制
view bookings_with_start with (security_invoker = true)
     -- bookings.* + 推導的 starts_at = MIN(starts_at)、ends_at = MAX(ends_at)
```

**函式與 trigger**：

```
create_booking(p_service_id uuid, p_start_slot_id uuid) returns uuid
  SECURITY DEFINER, set search_path = public
  -- 一個交易：讀 price 快照與 required_slots → 取 N 個連續時段（每格 ends_at 必須等於
  --   下一格 starts_at，否則 raise 'has a gap'）→ insert bookings + N 筆 booking_slots
  -- ⚠️ 所有 PL/pgSQL 變數都宣告在最上層的單一 declare，不可放進巢狀區塊
free_slots_on_cancel() + trg_free_slots_on_cancel
  -- status 變 cancelled 時刪掉該筆的 booking_slots，時段自動釋出
set_updated_at() + trg_bookings_updated_at
```

**EXECUTE 授權**（advisor 會抓）：

```
create_booking          → 只有 authenticated（已 revoke from public/anon）
free_slots_on_cancel    → 全部 revoke（trigger 仍照常觸發，它以 table owner 身分跑）
set_updated_at          → 全部 revoke
```

> **課程技能給的硬化語法不完整**：它只寫 `revoke ... from anon`，但 `PUBLIC` 身上的隱含 `EXECUTE`（ACL 的 `=X/postgres`）還在，anon 照樣繼承得到。要 `revoke ... from public` 再 `grant to authenticated`。

**超出課程 schema 的一項增補**：

```
uniq_slot_per_barber_start: unique index on bookable_slots(barber_id, starts_at)
```

起因：`/shop/bookings` 重複按發布會默默產生同一時間窗的多份副本，而 `create_booking` 是「依 starts_at 取下 N 個」，取到副本時第二份的 `starts_at` 不等於第一份的 `ends_at`，連續性檢查就誤判成有缺口 —— 多時段服務直接約不了。已用 migration 清掉 12 筆重複並加上這個索引。

**get_advisors（security）**：無 ERROR。三個 WARN 都是 checklist 明列的預期項 —— `create_booking` 對 authenticated 可執行（設計如此）、`is_admin()` 對 anon/authenticated 可執行（×2 算兩筆）、leaked password protection 未開。

## 驗收結果（m1.2-buyer-setup-checklist）

24 項全 ✅。幾個關鍵實測：

- **A3a `create_booking` 實測**（技能警告過的那個「schema 看起來對但 RPC 全壞」的巢狀 declare 作用域 bug）：回傳 booking id、`held_slots = required_slots`，然後 rollback，資料庫沒留測試列。
- **C4**：實際下訂一筆 N=3 的預約 —— `pending_payment`、`price=1800`（整數、非 ×100）、`paid_at`/`payout_id` 皆 NULL、起始時間 14:00–15:30 由 view 推導、3 筆 `booking_slots`、barber 透過 service join 取得。
- **C4b**：手動插第二筆 `booking_slots` 撞同一個 `slot_id` → `uniq_slot_held` 拋 unique violation。
- **C5**：那 3 格從可約清單消失，**且不需要重整**（query invalidate 生效）。
- **D3 用 SQL 切換身分驗**（比 UI 更嚴格）：擁有者看到 1、另一個登入者看到表 0、**看到 view 也是 0**（證明 `security_invoker` 讓 RLS 穿透 view）、擁有該理髮師的店家看到 1、陌生人仍讀得到 20 筆公開時段。
- **D4**：取消後 `held_slots` 歸 0、三格 `slot_bookable = true`。
- **D5**：整庫掃描 `0, 0, 0`。

## 工作方式（M1.2 期間修正的幾項）

**`npm ci` 在這個 repo 跑不動** —— `package-lock.json` 與 `package.json` 不同步（`ajv@6` vs `ajv@8`，M1.1 之前就有的既有問題；Vercel 用 `npm install` 所以沒炸）。沙箱要裝依賴用：

```bash
npm install --no-package-lock --no-audit --no-fund   # 約 50 秒
npm run build                                         # 約 7 秒
```

> 哪天 Vercel 改用 `npm ci` 這個 lockfile 就會直接紅，值得找時間修。

**`tsc --noEmit` 在這個 repo 是可用的真關卡** —— 和 supabase-best-practice 說的相反：那份技能說 vendored shadcn/Radix `ui/*` 會噴幾百個無關錯誤、不要拿來當關卡，但**這個 repo 的 `ui/*` 是 0 個錯誤**。而且：

- **沒有 `tsconfig.app.json`，只有 `tsconfig.json`** —— 用錯路徑時 tsc 吐 `TS5058`，若後面接 `grep '^src/'` 會把錯誤行濾掉、看起來像「零錯誤」。M1.2 期間就因此誤報過一次「驗證通過」，實際有兩個真錯誤。**驗證指令不要寫成會吞掉錯誤訊息的形式。**
- 這個 repo 開了 **`noUncheckedIndexedAccess`**（`arr[i]` 的型別是 `T | undefined`）和 **`exactOptionalPropertyTypes`**（傳 `undefined` ≠ 省略該 key）。

**`device_commit_files` 會依 staged path 快取內容** —— 同一個暫存路徑重送，工具回報 `written` 成功但寫進去的是**舊位元組**（mtime 更新、大小沒變）。每次改檔要換新的暫存路徑（例如 `outputs/m1.2/v2/`、`v3/`），並用 `device_list_dir` 的**檔案大小**核對是否真的落地。M1.2 期間踩到兩次。

**Supabase MCP 的 `execute_sql` 每個 statement 各自成一個交易** —— 技能給的 `begin; set local role ...; select create_booking(...); rollback;` 寫法無效，`set_config(..., true)` 的 transaction-local 設定活不到 RPC 那一步，`auth.uid()` 會是 NULL。正確作法是包成**單一 DO 區塊**，結尾用 `raise exception` 強制 rollback 並把結果塞進錯誤訊息：

```sql
do $$ declare v_id uuid; begin
  perform set_config('request.jwt.claims', json_build_object('sub', <customer>)::text, true);
  v_id := public.create_booking(<service>, <slot>);
  raise exception 'OK booking_id=%', v_id;   -- 強制 rollback
end $$;
```

**沙箱 `curl` 打不到 `supabase.co`** —— egress policy 擋掉（403）。線上服務要用內建瀏覽器或 Vercel MCP 驗，**不要把 curl 的 403 當成服務掛掉**。

**push 由使用者自己跑** —— git proxy 明確拒絕對此 repo 注入憑證（`not in this session's authorized repository set`，403）。若要讓 agent 直接推，需把 repo 加進 session 的 authorized sources。

**不要 force push / 改寫已發布歷史。**

**Claude 不能建立帳號或輸入密碼登入** —— 需要登入狀態的瀏覽器測試，要請使用者自己在瀏覽器面板登入後再接手。

## M2.1 的地基已經備好

M2.1 是**買家付款**：把 Book dialog 的 Confirm 從「只呼叫 `create_booking`」改成「`create_booking` 拿到 `booking_id` → 開 Stripe Checkout」，付款成功後 webhook 把 booking `pending_payment → paid` 並蓋 `paid_at`。

已就緒：

- **`create_booking` RPC 回傳 `booking_id`** —— Checkout 直接接在它後面，這個接縫是刻意留乾淨的。
- **`bookings.paid_at` / `payout_id` 欄位已存在**，目前全為 NULL；`status` 的 CHECK 已含 `paid`，不用改 schema。
- **`BookDialog` 的 `book` mutation 的 `onSuccess`** 就是要改的那一處（`src/components/book-dialog.tsx`）。
- **`errMessage()`** 已經在錯誤路徑上，webhook 或 Checkout 的錯誤訊息會如實顯示。
- **占位與付款無關** —— `booking_slots` 一寫入就佔住，`pending_payment` 和 `paid` 的持有效果相同，所以「誰先付款誰贏」只需要處理 webhook 那一側。

M2.1 會用到但**尚未具備**的：

- `commission_rates` 表（M2.1 建）
- `SUPABASE_SERVICE_ROLE_KEY` 放 Vercel **server** env（webhook 要它繞過 RLS；絕不進前端、不加 `VITE_` 前綴）
- **admin 帳號** —— M2.1 前置會要求用 migration 把某個帳號升級成 `role='admin'`（不可自助升級）
- Stripe 沙盒 `acct_1UENgjAXSjTQn8U8` 已連上，可直接用

> ⚠️ 這個 app 是**純靜態 SPA**（Vite + React Router，部署 `dist/`，`vercel.json` catch-all rewrite）—— **目前沒有任何 server route**。M2.1 的 Stripe webhook 需要 server 端，所以會是這個專案第一次引入 Vercel Functions（`api/` 目錄）。這是 M2.1 最大的結構性變化，別假設現有架構已經支援。
