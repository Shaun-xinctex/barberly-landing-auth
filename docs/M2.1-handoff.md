## 工作方式（M2.1 期間新學到的）

**`device_commit_files` 會破壞二進位檔。** 它把檔案當文字做 LF→CRLF 轉換，每個 PNG 固定膨脹 5770 bytes。`.claude/skills` 底下 m1.1 / m1.2 的 architecture PNG 早就因此壞掉（前幾次安裝造成的）。**技能圖檔要正確落地，必須在 Windows 端 git clone 後用 `robocopy` 直接複製**，不能經由 commit_files。純文字檔不受影響。

**Vercel 的 Redeploy 會搶走正式網址的別名。** push 之後如果又對「上一筆部署」按 Redeploy，那筆重建的是**舊 commit**，而且因為時間較新會奪走 production alias —— 等於用舊程式蓋掉剛推的新程式。M2.1 期間踩到一次，症狀是 `/api/stripe/webhook` 回 HTML 外殼，看起來像 `vercel.json` 沒修好，其實程式碼是對的。**push 後讓它自動部署就好，不要手動 redeploy**；真要 redeploy 一定確認那筆的 commit 訊息。

**Supabase 的 to-one embed 型別會騙人。** 產生的 TS 型別說 `booking.services` 是物件，但 runtime 由 PostgREST 怎麼讀 FK 決定，可能回**單元素陣列**或 **null**。直接讀 `service.barber_id` 是只在 production 才會炸的 TypeError。`api/bookings/checkout.ts` 用一個 `one()` 函式正規化，且**整個 handler 包 try/catch**，每個失敗點回帶 `stage` 的 JSON（`input` / `load-booking` / `status` / `embed-service` / `load-settings` / `stripe` / `unhandled`）。沒有這個，失敗就是一個沒有 body 的裸 500。

**孤兒 `pending_payment` 預約。** `createBooking` 跑在 checkout 呼叫**之前**，所以 checkout 失敗會留下一筆佔著時段的 `pending_payment` 預約。`book-dialog` 的 `onError` 現在也會 invalidate 時段清單 —— 否則使用者會一直重選那個被自己孤兒預約佔住的時段，一直拿到「just taken」。**要清掉就到 `/bookings` 取消**（trigger 會刪 `booking_slots` 放回時段）。

**取消後的預約日期會顯示「—」，這是正常的。** 開始時間是 view 用 `MIN(starts_at)` 從 `booking_slots` 推導的，取消的 trigger 會刪掉那些 join 列來釋出時段 —— 釋放時段和保留顯示時間在這個 schema 下互斥。**不要為了修這個去加快照欄位**，那會違反課程「時間必須推導、不可存」的規範。

**`tsconfig.json` 的 include 已加入 `api/**/*.ts`。** 原本只涵蓋 `src/`，serverless function 等於沒被檢查。加進去之後 `tsc --noEmit -p tsconfig.json` 對三個函式也是真關卡（`noUncheckedIndexedAccess`、`exactOptionalPropertyTypes` 都適用）。

**`eslint src` 有 440 個既有的 prettier 格式錯誤**（`Login.tsx`、`MyBookings.tsx`、`ShopBookings.tsx`、`ShopOnboarding.tsx`），M2.1 之前就存在，沒有處理 —— 全 repo reformat 會產生一大坨無關 diff。M2.1 新增/修改的檔案 lint 是乾淨的（EXIT=0）。

**沿用 M1.2 的既有事項**：`npm ci` 跑不動（lockfile 與 package.json 不同步），用 `npm install --no-package-lock --no-audit --no-fund`；沒有 `tsconfig.app.json`；沙箱 `curl` 打不到 `supabase.co` **也打不到 `*.vercel.app`**（egress policy，403）—— 驗線上服務要用 Vercel MCP 的 `web_fetch_vercel_url`（只能 GET）或 `get_runtime_logs`；push 由使用者自己跑（git proxy 拒絕對此 repo 注入憑證）；不要 force push。

## M2.2 的地基已經備好

M2.2 是**平台撥款給店家**：admin 挑出「欠撥」的預約（`status='paid'` 且 `payout_id IS NULL`）、依店家組成撥款批次、用 `commission_rates` 算 20/80 拆帳，並把 `payout_id` 蓋回那些預約。

已就緒：

- **`commission_rates` 已建好並 seed**（`2026-01-01 = 0.2000`），RLS 是「公開可讀、只有 admin 可寫」。
- **欠撥池已經有資料**：1 筆 `paid` 且 `payout_id IS NULL` 的預約（`price 1800`）。
- **`bookings.payout_id` 欄位已存在**，目前全為 NULL；webhook **從不碰它**，所以它乾淨。
- **`role='admin'` 帳號已備好**（`shaun@xinctex.com`）。
- **`is_admin()` 函式已存在**（M1.1 建的），`commission_rates` 的寫入政策就用它。
- **店家的銀行資料在 `profiles`**（`bank_account_name` / `bank_account_number`，只有本人與 admin 可讀），撥款頁要顯示的就是它。
- **`profiles.display_name`** 是店名（BOBO），M2.2 的撥款批次要快照它。
- **server 端基礎設施已經有了** —— `api/` 目錄、`_supabaseAdmin.ts` 的 service-role client、`vercel.json` 的 `/api/` 排除規則都在，M2.2 要加 route 直接沿用。

M2.2 會用到但**尚未具備**的：

- `payouts` 表與（技能大概會叫的）`owed_bookings` view
- `/admin/payouts` 頁面本身
- `routeForRole()` 的 admin 分支（建好頁面後再加，目前 admin 會落在 `/barbers`）

> **拆帳的算法方向**（M2.1 技能的註記）：`shop_cut = gross - round(gross × platform_pct)`，讓平台與店家兩邊加總剛好對得起來；並且把當下的費率**快照到批次列上**，之後改費率不會動到已結算的批次。
